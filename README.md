# idtrack-web

[![api](https://github.com/theislab/idtrack-web/actions/workflows/api.yml/badge.svg?branch=main)](https://github.com/theislab/idtrack-web/actions/workflows/api.yml) [![web](https://github.com/theislab/idtrack-web/actions/workflows/web.yml/badge.svg?branch=main)](https://github.com/theislab/idtrack-web/actions/workflows/web.yml) [![version](https://img.shields.io/github/v/tag/theislab/idtrack-web?label=version&sort=semver)](https://github.com/theislab/idtrack-web/tags) [![idtrack on PyPI](https://img.shields.io/pypi/v/idtrack.svg?label=idtrack)](https://pypi.org/project/idtrack/) [![idtrack's documentation](https://img.shields.io/readthedocs/idtrack/stable.svg?label=idtrack%20docs)](https://idtrack.readthedocs.io/en/stable/) [![license](https://img.shields.io/github/license/theislab/idtrack-web)](LICENSE)

The web application of [idtrack](https://github.com/theislab/idtrack): convert gene identifiers through Ensembl releases, genome assemblies and external databases from a browser or over HTTP, without installing idtrack or building its graphs.

idtrack is the library and holds no web code; this project depends on it as a package and carries its version: idtrack, this repository and idtrack's benchmarks ([idtrack-reproducibility](https://github.com/theislab/idtrack-reproducibility)) have one version number, each release tags all three `v<version>`, and the api of a version is locked to idtrack's tag of that version. What idtrack does, how it answers and what it does not do: its [documentation](https://idtrack.readthedocs.io/en/stable/). Setting the project up, configuring, testing, running and deploying it: [SETUP.md](SETUP.md).

| `web/` | The frontend (TypeScript, React, Vite), its unit tests `web/tests/` and end-to-end tests `web/e2e/`; built against `api/openapi.json` only |

| `deploy/` | The container file, the compose file with Caddy, the settings of the Helmholtz virtual machine (`deploy/vm/`: compose overrides, the Caddy files for each way to a certificate, updates, reboots, the journal's bounds, the weekly check), the systemd alternative, the publishing command's wrapper and the store's pruning |
| `scripts/` | Development helpers: `check.sh` (every check of the api and the frontend, in one run and one table: `scripts/check.sh`), the endpoint check against a running server, the builder of the tests' small graph |
| `.github/workflows/` | CI: lint, type check and tests of the api (`api.yml`) and of the frontend, with its end-to-end tests against the api (`web.yml`) |

The api and the frontend share nothing but `api/openapi.json`, which the api generates and a test keeps equal to what it serves.

## The api

Every endpoint is under `/api/v1`, keyless and read-only; an organism is named by its Ensembl production name (`homo_sapiens`) or a short name idtrack declares (`human`). Where to read about it:

- `GET /api/v1` names every endpoint; `/api/v1/openapi.json` describes each (parameters, fields, closed sets of codes as enumerations, the error codes of each endpoint, the headers, a recorded answer of each, the columns of the batch's table);
- `/llms.txt` and `/llms-full.txt` say the same for language models and other programs (written by the api from that document and its tables);
- the page `/developers` is the reference for people, with a console per endpoint.

A first request: the symbol `AGPAT9` as a list of release 80 wrote it, in HGNC symbols of release 115 (the graph's last).

```console
$ curl -s 'https://<server>/api/v1/organisms/human/convert?identifier=AGPAT9&from_release=80&final_database=HGNC%20Symbol'
{"query_id":"AGPAT9","graph_id":"AGPAT9","match":"exact",...,"from_release":80,"from_release_inferred":false,...,
 "to_release":115,"final_database":"HGNC Symbol","candidates":[{"gene":"ENSG00000138678.12","target":"GPAT3",...,"best":true,...}],
 ...,"status":"converted",...}
```

Without `from_release` the same symbol is read at 115, where it is a synonym of two genes: `"status":"tie"`, the best answers `GPAT3` and `LPCAT1`. The release an identifier is read at is idtrack's rule, stated in the document and in `/llms-full.txt`; `POST .../source-inference` tells which release a whole list fits.

**Results are idtrack's own.**

- A result is the `to_dict()` of idtrack's result object, written as JSON as it is: no field renamed, no number rounded (a float is written as the shortest text that reads back as the same double, which JavaScript's `JSON.parse` also reads exactly), no value reformatted. idtrack never puts NaN or infinity in a result; one that held either would be refused (a `500`), never sent.
- The one field the api adds is `error.code` of a batch item whose conversion failed: the stable code the same identifier sent alone would be answered with (`missing_value`, `search_budget_exceeded`, ...), beside idtrack's class name in `error.type`.
- The response schemas in `api/openapi.json` are made from idtrack's result classes and their documentation, so they say what each field means, and their closed sets of codes are enumerations from the tables of `/vocabulary`.
- `GET /organisms/{organism}/databases` says what each database a conversion can end in holds, from the graph's own record: `kind` (`ensembl`, one of idtrack's two gene namespaces, `versioned` or not; `accession`; `label`, a database of symbols or other names), whether it is a name authority's, the database of an accession database's labels (`EntrezGene`, NCBI's gene numbers, has its official symbols in `NCBI gene (formerly Entrezgene)`), and the names Ensembl gave it before.
- `POST /organisms/{organism}/source-inference` answers idtrack's `API.source_inference` for a list (the releases, assemblies or databases it fits), and `GET /organisms/{organism}/convert/each-database` one identifier converted into every database of a release, each as `/convert` answers it.
- Two endpoints answer from work done once when the server starts, before the workers are forked: `/organisms/{organism}/showcase`, conversions chosen to show the kinds of journey and phenomena of Ensembl's history (`api/idtrack_web_api/showcase_data/<organism>.json`; the home page's figures), each answered with `explain=true` exactly as `/convert` answers it, its cases given only where the graph is the one they were checked on; and `/organisms/{organism}/history`, Ensembl's gene id history in the graph counted per release and per transition from idtrack's public graph interface (gene versions active, ids created, history edges by plain fact: a new version, another id, the same version kept with a score, a retirement; and the fan of Ensembl's mapping: the gene versions with edges to two or more distinct versions across a pair of releases, and those reached from two or more), never idtrack's classification of an event (a split or a merge of `PathStep.reason` is idtrack's reading of a path's step).
- `?format=tsv` of a batch answers a table, one row per candidate: its columns, and how each is written, are in the document (`x-columns` and the description of the `200` answer's `text/tab-separated-values`; `error_code` among them).

**Every input is checked on the server**, and its cost bounded before any work.

- By the api, before idtrack is called: a path and query over 16 KiB is `414`; unknown or repeated query parameters are refused in time linear in the query; a query's values are UTF-8 once percent-decoded (as a body must be); a release is a whole number from 0 to 999,999,999, digits only in the query and a JSON integer in a body, the same rule in both, whether the graph covers it being idtrack's to answer; a query's boolean is `true` or `false`; a body is UTF-8 JSON (a leading byte order mark is ignored, as RFC 8259 allows), read by the api's own reader with no key twice, no NaN, no number of more than 4,300 digits and no nesting deeper than the parser reads, its unknown keys refused before the rest is read, and at most 20 problems listed with a count of the others; lengths; the organism among those loaded.
- By idtrack against the loaded graph (releases, databases at the release, identifiers), whose refusal is answered with idtrack's own message (its list of the accepted values written as a reference to `allowed`, which carries them), the argument and the accepted values.
- Malformed input is a 4xx with `argument` naming the parameter at fault, never a `500`; a request the HTTP parser itself cannot read is answered in the same JSON (`400 invalid_request`, or `414` for a head over 64 KiB).
- One difference from idtrack is deliberate: an identifier or name holding control, surrogate, private-use or unassigned characters *inside it* is refused at the api, the input boundary, with `invalid_identifier` and a message naming their positions (in a batch, the whole batch, every such index in `details`), where idtrack itself would remove the control characters and read the rest (its match prefix `unicode`). White space at its ends (a space, a tab, a line break, as a list cut from a table keeps) is no part of an identifier, as idtrack reads it: it is passed on, idtrack reads the identifier without it, and `query_id` keeps the string as sent. An empty string or a spelling of a missing value is idtrack's to answer, as it answers it.
- A path of the api that ends in `/` is redirected (`308`) to the path without it; a path that is no endpoint is a JSON `404` that names `GET /api/v1`.

Every failure is `{"error": {"code", "message", "argument", "allowed", "details", "request_id", "retry_after", "allowance"}}` with one of these codes (written from `api/idtrack_web_api/errors.py` by `idtrack-web docs`; `/vocabulary` serves the same table with a short title for people per code):

idtrack's input errors map by class (`UnknownReleaseError` to `unknown_release`, ...); a refusal of idtrack's that the api's own checks make unreachable through its endpoints (a wrong type, an inactive release, an unknown version or assembly) has no code of its own and would be answered as `invalid_input`; any other error is `internal_error`, whose traceback goes to the server's log with the request id, never to the client. An identifier that is not in the graph is not an error: it is a result with status `not_found` and its reason, as idtrack answers it, and a version the graph does not hold is the status `unknown_version`, a result too. In a batch, one identifier's failure (its search over budget) is that item's `status: "error"` with its `error` and `error.code`, and the batch goes on.

**The server's load** (`GET /status`). A request reaches one worker, so the load is kept where every worker can read it: each worker writes its own facts into a table of shared memory made before the fork (its row, its requests answered and held, its searches running and waiting, its errors, a ring of its last 1,000 request durations, its requests per second), and a thread of each worker samples the process's CPU every second and its memory every 5 seconds; the master is sampled by whichever worker comes first. Any worker reads the whole table to answer, and keeps its answer for a second, so polling costs a few milliseconds a second at most. A worker that ends is not reported; its counts stay in the server's totals, the master counts it (`workers_exited`, `last_worker_exit_at`, from gunicorn's `child_exit`), and the requests a killed worker held are counted as lost (`requests.lost`). Requests to `/status` are counted apart (`requests.status_requests`), so watching the load does not change what it reports. The table's lock is taken back from a process that died holding it, and the master's files in `/proc` are read without it.

- **CPU share** of a process: the CPU time it used (user and system, all its threads) over the wall time between two samples; `1.0` is one core kept busy. It is counted in the kernel's clock ticks (10 ms), so one interval's share is exact to about 0.01 core. The server's `cores_used` is the sum over its processes; `share_of_available` divides it by the cores the server may use: its CPU affinity set, or fewer when a cgroup v2 `cpu.max` quota (of its cgroup or an ancestor, as a container sets) allows fewer (`source` says which).
- **Memory** of a process, from the kernel's `smaps_rollup`: **RSS**, its resident pages, which counts the pages the workers share with the master (the graphs, loaded once before the fork) in full in every process, so the RSS of the processes add up to more than the server holds; **PSS**, each resident page divided by the number of processes sharing it, so the sum of PSS over the processes is the server's real footprint; **USS**, the pages of the process alone (what it would free on exit). Reading PSS makes the kernel walk the process's page tables (about 23 ms for a process that holds the five graphs), hence the 5 seconds.
- **The limit** the server runs under: the smallest cgroup v2 `memory.max` of its cgroup and its ancestors, with that cgroup's `memory.current` (`source` `cgroup`; a container's or a job's limit); without one, the machine's total and available memory (`source` `meminfo`). cgroup v1 is not read.
- **Latency**: the nearest-rank p50, p95 and p99 and the maximum of the server's most recent 1,000 requests that ended in the last 5 minutes, from arrival to the last byte sent (`count` says how many). A request arrives when a worker has taken its connection; the time before, in the listen queue, is not part of it.
- **Requests waiting for a worker** (`requests.connections_waiting`): the connections in the kernel's listen queue that no worker has taken yet, as Linux counts them for the listening socket (`TCP_INFO`), and the searches a busy worker took and handed on to the queue the workers share (`requests.searches_queued`; "How it runs"), read when the answer is made. While every worker is in a search, the searches waiting for a worker are counted here and in `searches_waiting` (every search waiting to run: for a worker free of searches, or for a worker's own search thread).
- **Answers not yet taken** (`sending_bytes`, per worker and in all): the bytes of answers the workers hold for clients that have not read them yet, bounded per worker by `sending_max_bytes`.

Nothing that identifies the machine is in the answer (no host name, path, user, environment, command line or process id: workers are numbered by their row). Where a number cannot be measured (no `/proc`, off Linux) it is `null` and its field is named in `unavailable`; a worker's CPU is measured everywhere.

**What every answer says about itself.**

- `X-Request-ID`: the request's id (the client's own `X-Request-ID` where it sent one of 1 to 64 letters, digits and `._:-`, else one the server made), also `error.request_id` of a refusal and in the server's log line.
- `Server-Timing`, readable by any origin (`Timing-Allow-Origin: *` beside the open CORS policy): `app;dur=` the server's whole time on the request until its answer started, and for a request that searched (a conversion, a batch, a name, a source inference) `queue;dur=` the time it waited for a worker free of searches and for that worker's search thread, `search;dur=` the search's own time and `write;dur=` the writing (and compressing) of its answer, all contained in `app`, in milliseconds measured by the server from the moment a worker took the request's connection (the time the connection waited in the listen queue before is the client's to see); `cache;desc="hit"` for an answer sent again from the worker's memory, `cache;desc="revalidated"` for a `304`: `Server-Timing: app;dur=12.402, queue;dur=0.081, search;dur=11.734, write;dur=0.204`.
- `Idtrack-Version` and `Idtrack-Graph-Digest` on every answer of one graph (an endpoint under `/organisms/{organism}`): the idtrack that answered and the graph's content digest (as `/version` gives them), so that a stored answer is tied to its graph without a second request.
- `RateLimit-Policy` and `RateLimit` where the allowances apply (below): each allowance as the IETF draft on rate-limit fields writes a policy, and the client's standing in the one the request drew on.

**Repeated requests are cheap.** An answer is a function of the graphs and the arguments, so every `GET` of the api but `/health` and `/status` has an `ETag` (the server's identity, made once at its start from its start time, versions and graphs, and the request's path and query, digested) and `Cache-Control: public, max-age=600`: a browser reuses an answer for ten minutes, then revalidates it, and `If-None-Match` naming the tag (weak or strong, either encoding) is answered `304` at once, without a search. Each worker keeps the answers it sent in memory up to `IDTRACK_WEB_ANSWER_CACHE_BYTES` (64 MiB; an answer over an eighth of it is not kept) and sends one again without a search. An answer of the api of 1 KiB or more goes compressed with gzip to a client that accepts it (decoded, its bytes are the endpoint's exactly; its `ETag` then ends in `-gzip`). The graph-wide tables idtrack computes lazily on a conversion's path (the facts by which it counts genes, about 12 to 15 s and 0.8 GB for the human graph) are computed in the master before the fork, so every worker shares them: the first search of `Q9Y6K9` from release 70 to `HGNC Symbol` in a fresh worker took 28.6 ms and 41.0 ms of search (each of the two workers of a server holding the five graphs). The texts for programs (`/llms.txt`, `/llms-full.txt`) are sent compressed too, with an `ETag` and `no-cache`, so a client revalidates them.

**Each client's allowances** (`api/idtrack_web_api/limits.py`; a client is its address, an IPv6 address by its `/64`):

- searching requests draw on a token bucket of `IDTRACK_WEB_RATE_PER_MINUTE` per minute with bursts of `IDTRACK_WEB_RATE_BURST`;
- every other request of the api (the tables and documents answered from memory, an answer sent again from memory, a `304`) on a bucket ten times as large (`read_share` of `/limits`), so that a page's own reads never use up its searches; `/health` on none;
- the seconds a client's searches took, with the writing of their answers, are charged when the answer is written against `IDTRACK_WEB_RATE_SEARCH_SECONDS` per minute (30 s, a balance of at most 60 s), so that one address cannot keep the workers busy with a stream of large batches within its request rate;
- a client has at most `IDTRACK_WEB_RATE_CONCURRENT_SEARCHES` (2) searching requests in progress at once, from their admission until their answer is sent, so that a burst cannot take every worker before any of its time is charged, nor hold more answers than that which it is slow to read.

A search is admitted by these allowances when a worker routes its connection, before it waits for a worker free of searches ("How it runs"): a burst from one address is refused at once, never queued ahead of other clients' searches (measured on the five graphs: 30 batches sent at once from one address, 2 admitted and 28 refused in 2.2 s, health checks from elsewhere answered within 81 ms meanwhile). A refusal is `429 rate_limited` with `Retry-After`, the same seconds in `retry_after` of the error, and the allowance used up in `allowance`. All of them are kept in shared memory made before the fork, so they are the server's, not a worker's; `IDTRACK_WEB_RATE_PER_MINUTE=0` turns them off (`allowances_enforced` of `/limits` says which).

**Bounds** (all set by environment variables, SETUP.md; `GET /limits` reports a server's own):

- a time budget per request (default 20 s, counted from the moment a worker took its connection, so a search that waited for a worker too long is refused rather than run) and per identifier's search (10 s, 200,000 states);
- at most 1,000 identifiers per batch, 256 characters per identifier, 1 MiB of request body and 32 MiB of answer: a larger answer is refused, never cut, and stops being written as soon as it passes the bound (its writing measured and charged as the search's), with advice that fits the request (fewer identifiers for a list, no `explain` where it was asked);
- the allowances above; at most 64 searches per worker waiting for a worker free of searches (`503 server_busy` beyond);
- a request's head within 5 s of its connection being taken (else the connection is closed) and its body within 30 s (else `408 request_timeout`); at most 2,048 connections waiting in the listen queue (gunicorn's backlog, or the system's `net.core.somaxconn` when smaller);
- an answer is sent in pieces of 64 KiB, each once the connection has room for it: a client that takes none of it for `IDTRACK_WEB_SEND_SECONDS` (30 s), or takes it more slowly than 64 KiB a second after that, has its connection closed, and a worker holds at most `IDTRACK_WEB_SENDING_MAX_BYTES` (256 MiB) of answers its clients have not taken (an answer beyond is refused, `503 server_busy`). Measured on the five graphs with two workers and the allowances off: 60 connections from one address that each asked for a 26.6 MB answer and read nothing made each worker hold at most 320 MiB of its own memory (40 of the 60 refused), and the workers dropped what they held at the 30 s while the sockets stayed open;
- a request whose client closes its connection while it waits for a search thread is not searched, and a batch stops between its groups.

## The frontend

The page at `/` makes idtrack usable from a browser: convert one identifier (with every candidate ranked, the criterion that decided, and the path through the releases), convert a list (pasted or uploaded, exported as TSV or JSON exactly as the api returns them), look up names, read what each graph holds, read the http api's reference with examples that run and a console for every endpoint (`/developers`, with `/llms.txt` for language models), watch the server's load (a quiet reading in the header, every process in its panel), and how to cite idtrack. Its centre is the path view: the identifier's journey drawn along Ensembl's releases over the genome assemblies that serve them, each step in the hue of its kind (a version change or replacement, a split or merge with its score, a crossing through an external database, an assembly handoff), the chosen answer strong and the alternatives the engine considered light, every element focusable with the exact values the api returned, and the same path in words beside it; on a phone it is a vertical timeline. Its visual direction and how the path view encodes each step: [web/DESIGN.md](web/DESIGN.md); install, tests and end-to-end tests: [SETUP.md](SETUP.md), section 14.

What the page shows is the api's answer unchanged: identifiers, releases and scores as sent (a float written back as Python wrote it), shortened only by cutting digits in the drawing, with the full value on focus; the answer as sent is one click away. Unit tests check on recorded real answers of the pig and human graphs that the drawn path is the api's path step for step; end-to-end tests run every flow in Chromium at 1440 and 390 px in both themes, with axe-core on every state.

### Accessibility

The page aims at WCAG 2.2 level AA in both themes. What is checked, and how: every end-to-end flow runs axe-core on every state it reaches (the rules of WCAG 2.0 and 2.1, A and AA, and axe's best practices; a violation of serious or critical impact fails the run), at 1440 and 390 px in the light and the dark theme; the path view, the tables and the consoles are driven by keyboard alone; focus is checked in forced colours; every page is checked at 320, 768, 1024 and 2560 px for text cut by its box or a page that scrolls sideways (SETUP.md, 14.6); the page's own rules (one focus ring, colour never the only carrier of a meaning, no motion under `prefers-reduced-motion`) are in [web/DESIGN.md](web/DESIGN.md). A barrier found on the site is a bug: report it at [github.com/theislab/idtrack-web/issues](https://github.com/theislab/idtrack-web/issues), with the page's address and what you used to reach it.

## How it runs

- **Where it runs.** First on a Helmholtz virtual machine (Ubuntu 26.04 LTS, 8 vCPU, 16 GB, 50 GB of disk, security updates with a weekly reboot, reached from outside by https only): Docker Engine runs the image and Caddy with `deploy/compose.yaml` and the overrides of `deploy/vm/`, the graphs in a folder store on the machine's disk (SETUP.md, section 10, with its measured sizing, reboots, disk and certificates). The Hetzner node (section 11) and the setup without containers, under systemd (section 12), are the alternatives.
- **Processes, not threads.** A search is CPU-bound and holds the interpreter lock; idtrack measured that threads add no throughput. The server is gunicorn with uvicorn's worker: the master verifies and loads every graph once, then forks the workers, which start with the graphs in memory (shared page by page until written to; idtrack's later memory-mapped graph format will keep them shared). Each worker runs one search at a time on a thread beside its event loop, so it keeps answering the requests it holds (health checks, refusals) during a search.
- **Every worker takes every connection; a search goes to a worker free of searches** (`api/idtrack_web_api/server.py`). The workers share one listening socket and take connections from it at all times. A worker reads the request line of each connection it takes without consuming it and routes it by method and path: a request that does not search (a health check, `/status`, a table answered from memory, a file of the page, a refusal) is answered at once by the worker that took it, beside any search that worker runs; a search is first admitted by its client's allowances (its whole head read the same way, for the client's address), then kept by the worker that took it if that worker holds no search, and otherwise handed on, its request unread, through a queue the workers share (a pair of Unix sockets made before the fork, the connection passed as a file descriptor), from which the first worker free of searches takes it, in the order the searches arrived. A worker holds a search until its answer is written, not until a slow client has read it, and every answer closes its connection (`Connection: close`), so each request is routed afresh and no client is bound to one worker. A taken connection that has not sent its request's head within `IDTRACK_WEB_HEAD_SECONDS` (5 s) is closed, and until it has, it makes no worker busy. Uvicorn's own worker, by contrast, runs every request it takes in the process that took it, so a worker in a long search keeps taking (and queueing behind its search) the requests of client after client while another worker idles. Measured on the five graphs with two workers: with 30 batches of 1,000 identifiers with paths sent at once from 30 addresses, health checks took at most 50 ms and `/status` at most 53 ms (60 batches: 59 and 53 ms; `/status` counted up to 58 requests waiting for a worker); with one worker in a batch of about 4 s and the other in one of about 2 s, a single conversion sent just after was answered when the shorter batch ended (1.6 to 2.7 s in 12 trials), never behind the longer. The price: a connection per request (Caddy opens one to the api per request, while a browser keeps its own connection to Caddy), and a worker's answers to reads are slower beside its own search, which holds the interpreter lock most of the time (milliseconds, as measured above).
- **One module calls idtrack:** `api/idtrack_web_api/adapter.py` holds every call into idtrack and every name of it the api uses (arguments, result classes, errors, version); the api applies none of idtrack's rules itself (which releases, databases and identifiers a graph accepts is idtrack's answer, refused with idtrack's own message under a stable code). A change of idtrack's interface is a change of that module and its tests.
- **What the workers share is made before the fork:** the clients' token buckets, balances of search time and searches in progress, the queue of searches handed on and its count, and the table of the load (`/status`).
- **The page as sent.** With `IDTRACK_WEB_STATIC_DIR` the server sends the built frontend itself: its text files (HTML, JavaScript, CSS, SVG, JSON, source maps) compressed with gzip once at start and sent compressed to a browser that accepts gzip (`Vary: Accept-Encoding`; fonts and images go as they are); the files the build names by their content's hash (`/assets/`) with `Cache-Control: public, max-age=31536000, immutable`, every other file (the page itself above all) with `no-cache` and an `ETag`, so a browser asks again and gets `304 Not Modified` while it is unchanged. The page is sent with the answers every view asks first written into it (`/organisms`, `/version`, `/vocabulary` and `/limits`, each its text exactly as the api sends it, in a `<script type="application/json">` block the page reads before it asks anything), so that its first paint waits for no request of the api; its `ETag` is that of the page as sent, so a new build or a server with other graphs is a new tag. A path that is not a route of the page (`web/src/lib/routes.ts`), or the page of an organism the server does not hold, is answered with the page and `404`; a hashed file of the build the server started with is still sent from memory when a new build has replaced it on disk. Only the build's own files are sent: no hidden file (a name that begins with `.`) and nothing outside the build's folder, even through a link. Every answer carries a strict Content-Security-Policy (the page's own allows its files and its one inline script by its hash, read from the `index.html` that is sent, so the policy fits the page even after a new build is put in place under a running server, and admits no string into the DOM's script sinks: `require-trusted-types-for 'script'`; the api's allows nothing), `Permissions-Policy`, `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy`, `X-Content-Type-Options`, `X-Frame-Options` and `Referrer-Policy`; the access log escapes every value from the client, one request to a line.
- **Data.** Graph files are published (`idtrack-web publish`) as immutable objects named by their content, `idtrack/<graph format>/<organism>/<sha256>.npz`, beside a manifest `idtrack/<graph format>/manifest.json` that lists, per organism, the key, SHA-256 and size, the snapshot release, the content digest and the idtrack that built the graph (`data/manifest.schema.json`). The store is a Cloudflare R2 bucket (S3 api) or a folder with the same layout on the server's disk (the virtual machine's, or the Hetzner node's). At start the server reads the manifest, fetches what its cache lacks (to a temporary name, renamed only once verified), verifies the size and SHA-256 of every file, loads the graphs, checks that each is the graph the manifest names, and refuses to start on any mismatch. Configuration is by environment variables only; no credential is in the repository, the image or the log.
